# Usage attribution

Usage in the native client and Costs → Usage in Dashboard share
`GET /v1/usage/breakdown`. Collection starts after upgrade; historical usage
is retained without inventing attribution for old requests.

The provider usage total records each observed model HTTP request, including
intermediate tool rounds, session planner calls and retries with reported usage.
Runtime generateText accepts an optional explicit channelId so planners can
persist their own request against the correct session. Unscoped auxiliary
generations and the separate routing meter are not assigned to a chat. Cache and reasoning
are provider detail counters and are not added again to the total. Request IDs
make persistence idempotent. Parallel sessions have independent observation
scopes. The existing token-usage API receives one row per reported request;
legacy observers do not save the same usage again.

Attribution counts arguments generated by the model, bounded results actually
sent back, repeated input history, advertised tool schemas, skill catalog
entries, and skill file reads. The first result inclusion is separate from
replay. Replayed arguments are input tokens in addition to their original output
count. Schemas and catalog entries are charged for every request in which they
are included, even without an invocation. Removed history stops accumulating
replay; compaction summaries are common context. Restored input-only calls are
marked as replay with incomplete generation attribution; they never invent new
invocations. In-memory call metadata is pruned to IDs present in the actual
request, plus newly generated calls.

Local token counts use bundled cl100k_base/o200k_base vocabularies and the pinned
SwiftTiktoken snapshot. Only explicitly supported OpenAI model identifiers select
an encoding. Other models use a marked character-based estimate. Local counts
cover visible payloads, not provider message formatting, hidden reasoning or
exact billing. They are not forced to sum to the provider total.

Tool and skill views overlap: a files.read result can also be skill instructions.
Do not add the two views. Skill counts mean instructions loaded, not verified
skill execution. Skill file membership uses registered directories, normalized
paths, actual read-result paths and symlink resolution. Failed reads do not add
skill result tokens.

MCP grouping uses catalog server IDs; explicit mcp.call_tool arguments also
identify the target server and tool. The model usage internal to an MCP server
and counterfactual token savings are unavailable. ACP and external agent
internals are not observed. Gemini tool calls without wire IDs, media and remote
conversation state are marked as incomplete attribution; their provider-reported
usage is retained. No additional token-counting or model API requests are made.

The endpoint supports from/to, channelId/sessionId, provider/model, serverId,
groupBy=tool|server|skill, groupId, cursor and limit (1–200, default 50).
Groups are sorted by descending attributed tokens. Calls have stable cursor
pagination. Provider totals and group aggregates cover the full filtered period
in SQLite, independent of pagination. A server-filtered provider total describes
whole model requests involving that server; it is not that server's billed cost.

The response includes collectionStartedAt, observed request count, reported
request count and complete attribution count. Unavailable values are never
shown as exact zero. Arguments/result/replay breakdowns remain local counts or
estimates; the precise counting method is shown alongside each group.

Statistics store metadata and counts only, without copying request or result
payloads. Vocabulary provenance and checksums are documented in
Packages/SwiftTiktoken/README.md.
