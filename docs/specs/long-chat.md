# Long chat

Long chat is the default persistent project session (`kind: long_chat`) per authenticated user, native-runtime agent and project. A global long chat remains available separately. Dashboard opens the project coordinator automatically and offers **Main chat** in the session list. Native exposes chat management in the existing **+** composer menu, without a separate row of mode buttons. **New separate chat** explicitly creates an ordinary session. Existing root project chats are upgraded on opening the project coordinator, retaining their session IDs, titles, timestamps and messages. Task, workspace and nested sessions retain their existing behavior; explicitly separate chats stay ordinary across restarts. ACP runtimes retain ordinary project chats. Child worker sessions (`long_chat_worker`) are excluded from the top-level session listing. Their bootstrap does not copy the parent conversation; their objective supplies the relevant context.

The coordinator can discuss, read through explicitly permitted tools, save agent-local memory, and manage assignments. Core rejects writes, shell, unknown MCP tools and synchronous delegation before tool authorization or approval escalation. MCP tools are eligible for reading only when discovery supplies an explicit `readOnlyHint`; the original agent policy still applies. Worker tool scopes are calculated independently from the agent's original policy. The coordinator chooses `readOnly` for each task; omitted values retain the legacy default based on whether the submitted resource list is empty. Execution workers can use `runtime.exec` according to their inherited tool policy. Read-only workers can request `runtime.exec`, including when the agent policy disables it, but Core requires approval before executing it. Other mutation and unknown-effect tools remain unavailable to read-only workers. Mutating tasks need resource keys. Project scope supplies canonical project/checkout keys. Read-only tasks can run alongside mutations of the same resource. Recursive delegation and shared-memory writes remain unavailable to workers. Workers can discover, read and message other agent sessions through the session collaboration tools, subject to the original agent policy.

For subagent tool approvals, the configured semantic decision provider (JEV or Laya) reviews the exact tool call with the original user request, delegated objective, acceptance criteria, read-only flag, resource keys, working directory and requested access. This review is independent of executor-model routing. Confident approval grants only that invocation; confident rejection prevents execution. An unavailable provider, missing authorization context, oversized context, an unknown decision, low confidence, or `ask_user` falls back to the existing approval flow. Human approvals appear on the parent Conversation and remain scoped to the child. Read-only shell calls require review even when an autonomous session normally bypasses approvals. Cancelling or replacing the worker while approval is pending prevents the approved call from executing.

`long_chat.delegate` accepts an `assignment` JSON string containing `requestKey`, `title`, `acceptanceCriteria`, and `tasks`. Each task has `key`, `title`, `objective`, `resourceKeys`, `dependsOn`, and optional `projectId` (defaults to the coordinator’s project). Keys within an assignment must be unique and dependencies must form a DAG. The stable request key deduplicates delegation within its source message. Include exact links, paths, authorizations and relevant background in each objective; workers do not inherit the complete transcript.

Accepted messages and worker notifications use a persisted inbox. Delegation returns an assignment and task/attempt IDs immediately; session and runtime worker IDs appear when a queued task starts. Each conversation runs at most three workers. Resource locks span conversations, including workers waiting for input. The configured semantic model router evaluates individual worker turns, while the coordinator retains its own model selection.

Workers finish with `agent_delegate.finish`, including status, summary, evidence and artifact links. Plain text without a completed structured result is a failure. Completed results and input requests generate `long_chat_task` session events and separate coordinator turns. Repeated delivery uses stable event/response IDs. Clarifications are persisted and serialized after the current worker turn. Cancellation records its terminal state before stopping the session and runtime worker; resource locks are released after stopping. Retries retain previous attempts, with at most two automatic retries. Permission blockers and interrupted operations cannot be retried automatically.

A Core restart restores queued work and waiting input. In-flight operations are marked interrupted and require inspection/manual retry rather than replaying potentially completed external mutations. Assignment snapshots are supplied on every coordinator turn, independently of model context compaction. Long chat sessions and their worker histories are exempt from automatic session retention.

## API

- `POST /v1/agents/:agentId/long-chat`: atomically open/create the authenticated user's session; optional `projectId` selects an independent project scope. The legacy `userId` body field is ignored in favor of the authenticated identity, or `local` when identity auth is disabled.
- `POST /v1/agents/:agentId/sessions`: root project requests open the main long chat by default; `separateChat: true` creates an ordinary session and durably excludes it from migration.
- Existing session message POST: returns a receipt immediately for long chat; the server serializes coordinator turns.
- `GET /v1/agents/:agentId/sessions/:sessionId/long-chat`: assignments, tasks and attempts.
- `POST .../long-chat/cancel`: cancel all active tasks.
- `POST .../long-chat/tasks/:taskId/cancel` or `/retry`: manage one task.
- `POST .../long-chat/tasks/:taskId/messages`: clarification with `content` and optional `clientMessageId`.
- Existing child-session input-answer and approval APIs: answer the worker directly.

State is atomically stored under `workspace/long-chat/state.json`; conversations and detailed worker transcripts retain existing JSONL session storage. Corrupted state fails explicitly rather than replacing the assignment ledger with an empty one.

Telegram, Discord and TUI long-chat interfaces are deferred. ACP runtimes cannot enable this mode because their external built-in tools cannot be restricted by the Core coordinator policy.

Visor never cancels workers based on total age, including Conversation and autopilot workers. The legacy `visor.workerTimeoutSeconds` setting remains decodable but is ignored, and legacy `visor.worker.timeout` events cannot stop execution. Completion, failure, user cancellation and restart recovery retain their existing owners. Swarm waits for task state changes without a fixed batch deadline and exits on explicit cancellation. `runtime.exec` retains its independent policy-capped command deadline; workers should omit `timeoutMs` for long builds to use the configured maximum.
